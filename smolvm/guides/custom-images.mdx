By default, SmolVM boots a minimal Alpine Linux image with SSH. If you need specific packages, libraries, or a different base OS, you can build a custom image using the `ImageBuilder` class. Custom images are built with Docker and cached locally so you only build once.

## Quick start

```python
from smolvm import SmolVM, VMConfig
from smolvm.build import ImageBuilder, SSH_BOOT_ARGS

builder = ImageBuilder()
kernel, rootfs = builder.build_alpine_ssh()

config = VMConfig(
    vm_id="my-custom-vm",
    vcpu_count=1,
    memory=512,
    kernel_path=kernel,
    rootfs_path=rootfs,
    boot_args=SSH_BOOT_ARGS,
)

with SmolVM(config) as vm:
    result = vm.run("cat /etc/os-release")
    print(result.output)
```

<Note>
  `ImageBuilder` requires Docker to be installed and running. On macOS, use Docker Desktop. On Linux, install `docker.io`.
</Note>

## Build methods

SmolVM provides three image build methods. Each creates a Linux filesystem with SSH pre-configured and returns a `(kernel_path, rootfs_path)` tuple.

### Alpine with SSH password

The simplest option — builds a minimal Alpine Linux image with root password authentication:

```python
kernel, rootfs = builder.build_alpine_ssh(
    name="my-alpine",           # Cache name (default: "alpine-ssh")
    ssh_password="mypassword",  # Root password (default: "smolvm")
    rootfs_size_mb=512,         # Disk size in MB (default: 512)
)
```

### Alpine with SSH key (recommended)

More secure — uses public key authentication instead of a password:

```python
from smolvm.utils import ensure_ssh_key

# Generate or load SSH keys
private_key, public_key = ensure_ssh_key()

kernel, rootfs = builder.build_alpine_ssh_key(
    ssh_public_key=public_key,
    name="alpine-key",
    rootfs_size_mb=512,
)

config = VMConfig(
    vm_id="key-vm",
    vcpu_count=1,
    memory=512,
    kernel_path=kernel,
    rootfs_path=rootfs,
    boot_args=SSH_BOOT_ARGS,
)

with SmolVM(config, ssh_key_path=str(private_key)) as vm:
    result = vm.run("whoami")
    print(result.output)  # "root"
```

### Debian with SSH key

For workloads that need `apt`, glibc, or broader package compatibility. Debian images are larger but more compatible:

<Note>
  Since v0.0.14, `debian` is no longer accepted by `smolvm create --os` or by auto-config. The `build_debian_ssh_key` method below remains available when you call `ImageBuilder` directly. For new projects, prefer the [Ubuntu auto-config path](/smolvm/concepts/published-images) or build on the Alpine/Ubuntu base.
</Note>

```python
from smolvm.utils import ensure_ssh_key

private_key, public_key = ensure_ssh_key()

kernel, rootfs = builder.build_debian_ssh_key(
    ssh_public_key=public_key,
    name="debian-key",
    rootfs_size_mb=2048,  # Debian needs more space
    base_image="debian:bookworm-slim",
)

config = VMConfig(
    vm_id="debian-vm",
    vcpu_count=2,
    memory=1024,
    kernel_path=kernel,
    rootfs_path=rootfs,
    boot_args=SSH_BOOT_ARGS,
)

with SmolVM(config, ssh_key_path=str(private_key)) as vm:
    result = vm.run("cat /etc/debian_version")
    print(result.output)
```

## Boot arguments

Use the `SSH_BOOT_ARGS` constant for any SSH-capable image on Firecracker:

```python
from smolvm.build import SSH_BOOT_ARGS

print(SSH_BOOT_ARGS)
# "console=ttyS0 reboot=k panic=1 pci=off root=/dev/vda rw init=/init"
```

<Warning>
  The `init=/init` parameter is required for SmolVM's SSH functionality. Without it, the custom init script will not run and SSH will not start.
</Warning>

### Boot args for any backend

`SSH_BOOT_ARGS` is wired for Firecracker on x86\_64. If you also run sandboxes on QEMU or libkrun — for example on macOS or arm64 hosts — use `DirectKernelBoot` instead. It renders the right kernel command line for each backend so you don't have to remember which flags belong where:

* Firecracker needs `pci=off`; QEMU and libkrun must not get it.
* QEMU on arm64 uses the `ttyAMA0` serial console; everything else uses `ttyS0`.
* Safe defaults like `tsc=reliable`, `no_timer_check`, and `quiet` are added automatically.

```python
from smolvm import DirectKernelBoot, SmolVM, VMConfig

boot = DirectKernelBoot(root="/dev/vda", init="/init")

config = VMConfig(
    vm_id="cross-backend-vm",
    vcpu_count=1,
    memory=512,
    kernel_path=kernel,
    rootfs_path=rootfs,
    boot_args=boot.render(backend="qemu", arch="host"),
)
```

`backend` accepts `"firecracker"`, `"qemu"`, or `"libkrun"`. `arch` accepts `"host"`, `"amd64"`/`"x86_64"`, or `"arm64"`/`"aarch64"`. Use `arch="host"` to match the current machine.

You can customize the profile when you need to:

```python
boot = DirectKernelBoot(
    root="/dev/vda",
    init="/init",
    console="serial",          # or "none" to drop console=...
    rw=True,                    # rw or ro
    quiet=False,                # show kernel log lines while debugging
    extra_args=("acpi=off",),  # one token per entry, no spaces
)
```

Set `SMOLVM_VERBOSE_BOOT=1` in your environment to drop the default `quiet` flag without changing your code — useful when debugging boot failures.

### Pick the right kernel for your backend

SmolVM publishes the same Linux 6.12.85 kernel in two formats. Firecracker and libkrun load the ELF artifact, while QEMU loads the Image/bzImage artifact. `ensure_base_kernel_for_backend` picks the right one, downloads and verifies it on first use, and caches it under `~/.smolvm/images/`:

```python
from smolvm import DirectKernelBoot, SmolVM, VMConfig, ensure_base_kernel_for_backend

backend = "qemu"
kernel = ensure_base_kernel_for_backend(backend, arch="host")

config = VMConfig(
    vm_id="cross-backend-vm",
    vcpu_count=1,
    memory=512,
    kernel_path=kernel,
    rootfs_path=rootfs,
    boot_args=DirectKernelBoot().render(backend=backend, arch="host"),
)
```

Use this whenever you supply your own rootfs but want SmolVM's verified kernel — for example, when boot-testing a custom image on both macOS (QEMU) and Linux (Firecracker) with one script.

## Bring your own Dockerfile

`ImageBuilder` bakes SmolVM's SSH guest agent into every rootfs. If you'd rather supply your own Dockerfile — for example to ship a custom init, a different control agent, or a minimal scratch image — use `DockerRootfsBuilder`. It builds a raw ext4 rootfs straight from your Dockerfile, caches the result by build inputs, and gives you back a `BootImage` you can boot on any backend.

Use `DockerRootfsBuilder` when:

* You don't want SmolVM's SSH agent inside the image.
* You already have a working Dockerfile and want to keep it as the source of truth.
* You want the same rootfs to boot on Firecracker, QEMU, and libkrun without rebuilding for each backend.

### Build a rootfs from a Dockerfile

```python
from smolvm import DirectKernelBoot, DockerRootfsBuilder

builder = DockerRootfsBuilder(
    name="scratch-demo",
    dockerfile="""
        FROM alpine:3.20
        RUN apk add --no-cache busybox-extras
        COPY init /init
        RUN chmod +x /init
    """,
    context={"init": "#!/bin/sh\nexec /bin/sh\n"},
    rootfs_size_mb=256,
)

image = builder.ensure(
    backend="qemu",
    arch="host",
    boot=DirectKernelBoot(root="/dev/vda", init="/init"),
)

print(image.rootfs_path)   # ~/.smolvm/images/custom/scratch-demo/<hash>/rootfs.ext4
print(image.kernel_path)   # SmolVM's verified kernel for QEMU/host arch
```

`ensure()` returns a `BootImage` describing the rootfs, the matching kernel, and the rendered boot arguments. It does not start a VM.

### Constructor options

| Option | What it does |
| --- | --- |
| `name` | Cache directory name. Letters, numbers, `.`, `_`, and `-` only. |
| `dockerfile` | Inline Dockerfile text. SmolVM writes it into a temporary build context. |
| `context` | Files to copy alongside the Dockerfile. Accepts `Path`, `str`, or `bytes` values keyed by safe relative paths. |
| `rootfs_size_mb` | Size of the raw ext4 rootfs (default `512`). |
| `cache_dir` | Where built rootfs artifacts and metadata live (default `~/.smolvm/images/`). |
| `fingerprint_inputs` | Extra JSON-serializable values to mix into the cache key — useful for tagging template versions. |
| `build_args` | `--build-arg` pairs forwarded to `docker build`. |
| `docker_platform` | Override the Docker target platform (defaults to `linux/amd64` or `linux/arm64`). |
| `ssh_capable` | Set `True` if your image ships an SSH server so downstream code can choose SSH transport. |

### Reuse one rootfs across backends

The cache key is built from the Dockerfile, the build context, `build_args`, the target arch, and your `fingerprint_inputs`. It deliberately leaves out the backend and the kernel identity, so Firecracker and QEMU share the same rootfs as long as the arch matches:

```python
qemu_image = builder.ensure(backend="qemu", arch="amd64", boot=DirectKernelBoot())
fc_image = builder.ensure(backend="firecracker", arch="amd64", boot=DirectKernelBoot())

assert qemu_image.rootfs_path == fc_image.rootfs_path
# Different kernels — same rootfs.
```

Boot in one place; switch hosts without rebuilding.

### Safety rules for build contexts

`DockerRootfsBuilder` rejects unsafe context paths before it touches Docker:

* Paths must be relative — no absolute paths or `..` traversal.
* A context entry named `Dockerfile` (any case) is reserved.
* Missing files referenced by `Path` raise a clear `ImageError` before the build starts.

## Describe a bootable image

`BootImage` is the small Pydantic model that ties a rootfs, a kernel, and boot metadata together. `DockerRootfsBuilder.ensure()` returns one, but you can also build one by hand if you already have rootfs and kernel artifacts on disk:

```python
from pathlib import Path

from smolvm import BootImage, DirectKernelBoot

image = BootImage(
    name="prebuilt-demo",
    rootfs_path=Path("/var/images/demo.ext4"),
    rootfs_format="raw-ext4",
    kernel_path=Path("/var/images/vmlinux.elf"),
    boot=DirectKernelBoot(root="/dev/vda", init="/init"),
    backend="firecracker",
    arch="amd64",
)

print(image.render_boot_args())   # rendered for firecracker / amd64
print(image.boot_mode)            # "direct_kernel"
```

`BootImage` validates that artifact paths exist, that `boot` and `boot_args` are not both set, and that direct-kernel images carry one of them. It does not allocate networking, clone disks, or start a VM — it is a description you can pass around.

### Firmware-booted images

For QEMU images that boot through firmware instead of `-kernel` (for example, a cloud image with its own bootloader), use the `FirmwareBoot` marker:

```python
from smolvm import BootImage, FirmwareBoot

image = BootImage(
    name="ubuntu-cloud",
    rootfs_path=Path("/var/images/ubuntu.qcow2"),
    rootfs_format="qcow2",
    boot=FirmwareBoot(),
    backend="qemu",
)
```

Firmware images must not set `kernel_path`, `initrd_path`, or `boot_args`, and only `qemu` is supported as the backend.

## Launch a BootImage with `SmolVM.from_image()`

Once you have a `BootImage`, the easiest way to boot it is `SmolVM.from_image()`. It builds the right `VMConfig` for you, downloads the matching base kernel when the image doesn't carry one, and lets you set per-VM knobs like memory and networking without touching backend internals.

Use it when you want a one-line launcher for a custom image while still controlling vCPUs, memory, networking, port forwards, vsock, and the host-to-guest control channel.

```python  theme={null}
from smolvm import SmolVM, DirectKernelBoot, DockerRootfsBuilder

builder = DockerRootfsBuilder(
    name="my-app",
    dockerfile="""
        FROM alpine:3.20
        RUN apk add --no-cache python3
    """,
)

image = builder.ensure(
    backend="qemu",
    arch="host",
    boot=DirectKernelBoot(root="/dev/vda", init="/sbin/init"),
)

with SmolVM.from_image(image, vcpus=2, memory_mb=1024) as vm:
    result = vm.run("python3 --version")
    print(result.stdout.strip())
```

A few things to know:

* `from_image()` resolves the backend and architecture from the image's metadata when you don't pass them, and only fetches a base kernel for direct-kernel images that omit `kernel_path`.
* Custom images without an SSH server keep working — SmolVM checks `image.ssh_capable` and skips SSH key setup when it's `False`. Use a vsock-based [control channel](/smolvm/concepts/control-channel) for those guests.
* `port_forwards` require `backend="qemu"` and `network="slirp"`. Other combinations raise a clear error before the VM starts.
* Firmware images (qcow2 cloud images, Windows guests, anything booted through OVMF) must run on QEMU; passing `backend="firecracker"` raises early.

See the full parameter list in the [`SmolVM.from_image()` reference](/smolvm/api/smolvm#from-image).

## Image caching

`ImageBuilder` caches built images to avoid rebuilding. The first build downloads base images and runs Docker. Subsequent calls with the same name return cached paths instantly:

```python
builder = ImageBuilder()

# First build — downloads and builds everything
kernel1, rootfs1 = builder.build_alpine_ssh(name="my-image")

# Second call — returns cached paths immediately
kernel2, rootfs2 = builder.build_alpine_ssh(name="my-image")
```

For key-based images, the cache is automatically invalidated if the SSH key is newer than the cached image.

### Custom cache directory

```python
from pathlib import Path

builder = ImageBuilder(cache_dir=Path("/mnt/fast-ssd/vm-images"))

kernel, rootfs = builder.build_alpine_ssh()
print(kernel)  # /mnt/fast-ssd/vm-images/alpine-ssh/vmlinux.bin
print(rootfs)  # /mnt/fast-ssd/vm-images/alpine-ssh/rootfs.ext4
```

## The kernel SmolVM uses

Every image you build with `ImageBuilder` boots SmolVM's own Linux 6.12.85 kernel. SmolVM builds it in CI from upstream Linux source and tunes it for sandbox workloads — it is the same kernel used by the [published images](/smolvm/concepts/published-images) so behavior stays consistent across hosts.

You don't need to pick a kernel or pass a URL. SmolVM downloads the universal kernel once and caches it under `~/.smolvm/images/<version>/`.

## How the init script works

All SSH-capable images include a custom `/init` script that runs as PID 1 inside the sandbox. This script:

* Mounts essential filesystems (`/proc`, `/sys`, `/dev`, `/tmp`)
* Configures networking from kernel boot arguments
* Sets up DNS resolution (8.8.8.8)
* Generates SSH host keys if missing
* Starts the SSH daemon
* Stays alive as PID 1 to keep the sandbox running

You do not need to modify this script for most use cases. It is included automatically when you use any `ImageBuilder` method.

## Real-world example: OpenClaw

<Tip>
  For day-to-day use, run `smolvm openclaw start` — it boots from a [pre-built image](/smolvm/concepts/published-images) in seconds and forwards your `OPENROUTER_API_KEY` and `OPENCLAW_GATEWAY_TOKEN` automatically. The example below shows the manual builder path, which is useful when you're customizing the image.
</Tip>

This example from `examples/openclaw.py` builds a 4 GB Debian image for the OpenClaw application:

```python
import os
from smolvm import SmolVM, VMConfig
from smolvm.build import ImageBuilder, SSH_BOOT_ARGS
from smolvm.utils import ensure_ssh_key

private_key, public_key = ensure_ssh_key()

kernel, rootfs = ImageBuilder().build_debian_ssh_key(
    ssh_public_key=public_key,
    name="debian-ssh-key-openclaw-4g",
    rootfs_size_mb=4096,
)

config = VMConfig(
    vcpu_count=1,
    memory=2048,
    kernel_path=kernel,
    rootfs_path=rootfs,
    boot_args=SSH_BOOT_ARGS,
    env_vars={
        "OPENROUTER_API_KEY": os.getenv("OPENROUTER_API_KEY", ""),
    },
)

with SmolVM(config, ssh_key_path=str(private_key)) as vm:
    vm.run("apt-get update && apt-get install -y nodejs npm")
    vm.run("npm install -g openclaw")
```

## Troubleshooting

When an image build fails, SmolVM diagnoses the root cause and returns a specific error message. You do not need to debug Docker issues manually.

<AccordionGroup>
  <Accordion title="Docker not installed">
    SmolVM raises an `ImageError` with install instructions:

    * **macOS**: Install [Docker Desktop](https://www.docker.com/products/docker-desktop)
    * **Linux**: `sudo apt-get install docker.io` (Debian/Ubuntu)

    You can check Docker availability before building:

    ```python
    builder = ImageBuilder()
    if not builder.check_docker():
        print(builder.docker_requirement_error())
    ```
  </Accordion>

  <Accordion title="Docker daemon not running">
    Start the Docker service:

    <Tabs>
      <Tab title="macOS">
        ```bash
        open -a Docker
        ```
      </Tab>
      <Tab title="Linux">
        ```bash
        sudo systemctl start docker
        ```
      </Tab>
    </Tabs>
  </Accordion>

  <Accordion title="Permission denied on Docker socket">
    Add your user to the `docker` group:

    ```bash
    sudo usermod -aG docker $USER
    newgrp docker  # or log out and back in
    ```
  </Accordion>

  <Accordion title="Build fails with disk space errors">
    Image builds require sufficient disk space. Check available space and clean the Docker cache if needed:

    ```bash
    df -h ~/.smolvm/images/
    docker system prune -a
    ```
  </Accordion>
</AccordionGroup>
