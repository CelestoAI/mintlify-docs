title: "Custom images"

Custom images let you start a SmolVM sandbox with your own tools already inside it. Use them when the default images are missing packages, system files, or startup behavior that your workload needs.

A custom image starts with a root filesystem, which is the disk image that contains the guest operating system files. SmolVM can build that disk from a Dockerfile, describe it with `BootImage`, and launch it with `SmolVM.from_image(...)`.

## Quick start

Start here when you want to prove that a Dockerfile-built image can boot. This example creates a tiny Alpine Linux image, starts it with QEMU, and prints the VM ID.

In the code below, `DockerRootfsBuilder` turns the Dockerfile into a disk, and `DirectKernelBoot()` uses SmolVM's default Linux boot settings for `/init`.

```python
from smolvm import DirectKernelBoot, DockerRootfsBuilder, SmolVM

dockerfile = """FROM alpine:3.20
RUN echo '#!/bin/sh' > /init
RUN echo 'mount -t proc proc /proc' >> /init
RUN echo 'mount -t sysfs sysfs /sys' >> /init
RUN echo 'mount -t devtmpfs devtmpfs /dev 2>/dev/null || true' >> /init
RUN echo 'while true; do sleep 3600; done' >> /init
RUN chmod +x /init
"""

image = DockerRootfsBuilder(
    name="tiny-alpine",
    dockerfile=dockerfile,
).ensure(
    backend="qemu",
    boot=DirectKernelBoot(),
)

with SmolVM.from_image(image, memory_mb=512) as vm:
    print(f"Started {vm.vm_id}")
```

The quickstart has one goal: boot a disk built from a Dockerfile. The sections below add command execution, reusable image metadata, disk resizing, and backend-specific boot settings.

## Choose a build path

SmolVM has three custom-image paths:

| Path | Use it when |
| --- | --- |
| `DockerRootfsBuilder` + `BootImage` | You want your Dockerfile to define the operating system files and startup process. |
| `ImageBuilder` | You want an Alpine or Ubuntu root filesystem with SSH already configured for `vm.run(...)`. |
| Manual `BootImage` | You already have a rootfs, kernel, or qcow2 image on disk. |

This guide starts with the Dockerfile path, then covers SSH-ready images, and leaves boot arguments for the advanced section.

## Bring your own Dockerfile

Use `DockerRootfsBuilder` when you want a Dockerfile to be the source of truth for the sandbox image. It builds a raw ext4 root filesystem, caches it by build inputs, and returns a `BootImage` you can launch with `SmolVM.from_image(...)`.

Use this path when:

* You already have a working Dockerfile.
* You want to choose the init process or guest agent yourself.
* You want one rootfs build to boot on both Firecracker and QEMU.

### Build a rootfs from a Dockerfile

The rootfs is the disk image that SmolVM boots. This example adds `busybox-extras`, copies a small `/init` script into the image, and prepares it for QEMU:

```python
from smolvm import DirectKernelBoot, DockerRootfsBuilder

builder = DockerRootfsBuilder(
    name="scratch-demo",
    dockerfile="""
        FROM alpine:3.20
        RUN apk add --no-cache busybox-extras
        COPY init /init
        RUN chmod +x /init
    """,
    context={
        "init": """#!/bin/sh
mount -t proc proc /proc
mount -t sysfs sysfs /sys
mount -t devtmpfs devtmpfs /dev 2>/dev/null || true

while true; do
  sleep 3600
done
"""
    },
    rootfs_size_mb=256,
)

image = builder.ensure(
    backend="qemu",
    arch="host",
    boot=DirectKernelBoot(root="/dev/vda", init="/init"),
)

print(image.rootfs_path)   # ~/.smolvm/images/custom/scratch-demo/<hash>/rootfs.ext4
print(image.kernel_path)   # SmolVM's verified kernel for QEMU/host arch
```

`ensure()` returns a `BootImage` describing the rootfs, the matching kernel, and the boot profile. It prepares the image metadata; it starts the VM only when you pass the image to `SmolVM.from_image(...)`.

<Tip>
  `DockerRootfsBuilder` gives you full control over the guest image. Use `ImageBuilder` instead when you want SmolVM to set up SSH for you.
</Tip>

### Constructor options

| Option | What it does |
| --- | --- |
| `name` | Cache directory name. Letters, numbers, `.`, `_`, and `-` only. |
| `dockerfile` | Inline Dockerfile text. SmolVM writes it into a temporary build context. |
| `context` | Files to copy alongside the Dockerfile. Accepts `Path`, `str`, or `bytes` values keyed by safe relative paths. |
| `rootfs_size_mb` | Size of the raw ext4 rootfs (default `512`). |
| `cache_dir` | Where built rootfs artifacts and metadata live (default `~/.smolvm/images/`). |
| `fingerprint_inputs` | Extra JSON-serializable values to mix into the cache key, such as a template version. |
| `build_args` | `--build-arg` pairs forwarded to `docker build`. |
| `docker_platform` | Override the Docker target platform (defaults to `linux/amd64` or `linux/arm64`). |
| `ssh_capable` | Set `True` only when your image starts SSH and accepts the credentials you pass to `SmolVM.from_image(...)`. |

### Reuse one rootfs across backends

The cache key is built from the Dockerfile, the build context, `build_args`, the target arch, and your `fingerprint_inputs`. It deliberately leaves out the backend and kernel identity, so Firecracker and QEMU share the same rootfs when the architecture matches:

```python
qemu_image = builder.ensure(
    backend="qemu",
    arch="amd64",
    boot=DirectKernelBoot(root="/dev/vda", init="/init"),
)
fc_image = builder.ensure(
    backend="firecracker",
    arch="amd64",
    boot=DirectKernelBoot(root="/dev/vda", init="/init"),
)

assert qemu_image.rootfs_path == fc_image.rootfs_path
# Different kernels, same rootfs.
```

### Safety rules for build contexts

`DockerRootfsBuilder` rejects unsafe context paths before it touches Docker:

* Paths must be relative. Absolute paths and `..` traversal are rejected.
* A context entry named `Dockerfile` is reserved.
* Missing files referenced by `Path` raise a clear `ImageError` before the build starts.

## Launch a BootImage with `SmolVM.from_image()`

Once you have a `BootImage`, pass it to `SmolVM.from_image(...)` to start the sandbox. SmolVM creates an isolated per-VM disk, picks the right backend settings, and applies runtime options such as memory and CPU.

```python  theme={null}
from smolvm import SmolVM

with SmolVM.from_image(image, vcpus=2, memory_mb=1024) as vm:
    print(f"Started {vm.vm_id}")
```

A few things to know:

* `from_image()` uses the backend and architecture recorded on the image when you do not pass them.
* Direct-kernel images can omit `kernel_path`; SmolVM resolves the matching base kernel.
* Boot-only custom images still start successfully. SmolVM checks `image.ssh_capable` before command helpers assume SSH is available.
* Firmware images such as qcow2 cloud images must run on QEMU.

See the full parameter list in the [`SmolVM.from_image()` reference](/smolvm/api/smolvm#from-image).

### Run commands from a custom image

`SmolVM.from_image(...)` starts the VM. Command helpers such as `vm.run(...)`, file upload, and environment variables need a guest control path.

Use one of these paths when you want guest commands:

* Use `ImageBuilder` for an SSH-ready Linux image.
* Add your own SSH server to the image, make sure it starts during boot, and set `ssh_capable=True`.
* Add your own guest agent and select a matching [control channel](/smolvm/concepts/control-channel).

<Warning>
  Set `ssh_capable=True` only when the image can accept SSH connections with the `ssh_user`, `ssh_key_path`, or `ssh_password` you pass to SmolVM.
</Warning>

### Resize the disk on launch

Most custom images ship at the smallest size that works for the base OS. When a workload needs more space, pass `disk_size_mb` to grow the per-VM disk. For raw ext4 images, set `grow_filesystem=True` so the guest sees the new space at boot.

```python  theme={null}
with SmolVM.from_image(
    image,
    memory_mb=1024,
    disk_size_mb=4096,
    grow_filesystem=True,
) as vm:
    print(f"Started {vm.vm_id} with a 4 GiB disk")
```

A few things to keep in mind:

* `disk_size_mb` only grows the disk. SmolVM rejects values smaller than the image's current size to avoid corrupting the filesystem.
* `grow_filesystem=True` requires `rootfs_format="raw-ext4"` and `e2fsprogs` (`e2fsck`, `resize2fs`) on the host.
* For `qcow2` images, SmolVM can grow the virtual disk size, and the guest remains responsible for growing its partition or filesystem.
* Both options need `disk_mode="isolated"` (the default). SmolVM never resizes a shared base image.

## Build SSH-ready images

`ImageBuilder` creates Linux filesystems with SSH pre-configured and returns a `(kernel_path, rootfs_path)` tuple. Use it when you want command execution through `vm.run(...)` and prefer SmolVM to provide the init script.

```python
from smolvm import SmolVM, VMConfig
from smolvm.build import ImageBuilder, SSH_BOOT_ARGS

builder = ImageBuilder()
kernel, rootfs = builder.build_alpine_ssh()

config = VMConfig(
    vm_id="my-custom-vm",
    vcpu_count=1,
    memory=512,
    kernel_path=kernel,
    rootfs_path=rootfs,
    boot_args=SSH_BOOT_ARGS,
)

with SmolVM(config) as vm:
    result = vm.run("cat /etc/os-release")
    print(result.stdout)
```


## ImageBuilder methods

`ImageBuilder` provides three build methods.

### Alpine with SSH password

The simplest option — builds a minimal Alpine Linux image with root password authentication:

```python
kernel, rootfs = builder.build_alpine_ssh(
    name="my-alpine",           # Cache name (default: "alpine-ssh")
    ssh_password="mypassword",  # Root password (default: "smolvm")
    rootfs_size_mb=512,         # Disk size in MB (default: 512)
)
```

### Alpine with SSH key (recommended)

More secure — uses public key authentication instead of a password:

```python
from smolvm.utils import ensure_ssh_key

# Generate or load SSH keys
private_key, public_key = ensure_ssh_key()

kernel, rootfs = builder.build_alpine_ssh_key(
    ssh_public_key=public_key,
    name="alpine-key",
    rootfs_size_mb=512,
)

config = VMConfig(
    vm_id="key-vm",
    vcpu_count=1,
    memory=512,
    kernel_path=kernel,
    rootfs_path=rootfs,
    boot_args=SSH_BOOT_ARGS,
)

with SmolVM(config, ssh_key_path=str(private_key)) as vm:
    result = vm.run("whoami")
    print(result.stdout)  # "root"
```

## Describe a bootable image

`BootImage` is the small Pydantic model that ties a rootfs, a kernel, and boot metadata together. `DockerRootfsBuilder.ensure()` returns one, but you can also build one by hand if you already have rootfs and kernel artifacts on disk:

```python
from pathlib import Path

from smolvm import BootImage, DirectKernelBoot

image = BootImage(
    name="prebuilt-demo",
    rootfs_path=Path("/var/images/demo.ext4"),
    rootfs_format="raw-ext4",
    kernel_path=Path("/var/images/vmlinux.elf"),
    boot=DirectKernelBoot(root="/dev/vda", init="/init"),
    backend="firecracker",
    arch="amd64",
)

print(image.render_boot_args())   # rendered for firecracker / amd64
print(image.boot_mode)            # "direct_kernel"
```

`BootImage` validates that artifact paths exist, that `boot` and `boot_args` are not both set, and that direct-kernel images carry one of them. It does not allocate networking, clone disks, or start a VM — it is a description you can pass around.

### Firmware-booted images

For QEMU images that boot through firmware instead of `-kernel` (for example, a cloud image with its own bootloader), use the `FirmwareBoot` marker:

```python
from smolvm import BootImage, FirmwareBoot

image = BootImage(
    name="ubuntu-cloud",
    rootfs_path=Path("/var/images/ubuntu.qcow2"),
    rootfs_format="qcow2",
    boot=FirmwareBoot(),
    backend="qemu",
)
```

Firmware images must not set `kernel_path`, `initrd_path`, or `boot_args`, and only `qemu` is supported as the backend.

## Image caching

`ImageBuilder` caches built images to avoid rebuilding. The first build downloads base images and runs Docker. Subsequent calls with the same name return cached paths instantly:

```python
builder = ImageBuilder()

# First build — downloads and builds everything
kernel1, rootfs1 = builder.build_alpine_ssh(name="my-image")

# Second call — returns cached paths immediately
kernel2, rootfs2 = builder.build_alpine_ssh(name="my-image")
```

For key-based images, the cache is automatically invalidated if the SSH key is newer than the cached image.

### Custom cache directory

```python
from pathlib import Path

builder = ImageBuilder(cache_dir=Path("/mnt/fast-ssd/vm-images"))

kernel, rootfs = builder.build_alpine_ssh()
print(kernel)  # /mnt/fast-ssd/vm-images/alpine-ssh/vmlinux.bin
print(rootfs)  # /mnt/fast-ssd/vm-images/alpine-ssh/rootfs.ext4
```

## The kernel SmolVM uses

Every image you build with `ImageBuilder` boots SmolVM's own Linux 6.12.85 kernel. SmolVM builds it in CI from upstream Linux source and tunes it for sandbox workloads — it is the same kernel used by the [published images](/smolvm/concepts/published-images) so behavior stays consistent across hosts.

You don't need to pick a kernel or pass a URL. SmolVM downloads the universal kernel once and caches it under `~/.smolvm/images/<version>/`.

## How the init script works

All SSH-capable images include a custom `/init` script that runs as PID 1 inside the sandbox. This script:

* Mounts essential filesystems (`/proc`, `/sys`, `/dev`, `/tmp`)
* Configures networking from kernel boot arguments
* Sets up DNS resolution (8.8.8.8)
* Generates SSH host keys if missing
* Starts the SSH daemon
* Stays alive as PID 1 to keep the sandbox running

You do not need to modify this script for most use cases. It is included automatically when you use any `ImageBuilder` method.

## Advanced boot settings

Boot arguments are settings passed to the Linux kernel before the guest starts. Most custom images can use `DirectKernelBoot()` or `SSH_BOOT_ARGS` and skip this section.

### Use `SSH_BOOT_ARGS` for SSH-ready images

Use the `SSH_BOOT_ARGS` constant for images built with `ImageBuilder`:

```python
from smolvm.build import SSH_BOOT_ARGS

print(SSH_BOOT_ARGS)
# "console=ttyS0 reboot=k panic=1 pci=off root=/dev/vda rw init=/init"
```

<Warning>
  The `init=/init` parameter starts SmolVM's SSH init script. Keep it when you want an `ImageBuilder` image to accept SSH connections.
</Warning>

### Render backend-specific arguments

Use `DirectKernelBoot` when the same rootfs may boot on QEMU and Firecracker. It renders the right kernel command line for each backend:

* Firecracker gets `pci=off`.
* QEMU skips `pci=off`.
* QEMU on arm64 gets the `ttyAMA0` serial console.
* Safe defaults like `tsc=reliable`, `no_timer_check`, and `quiet` are added automatically.

```python
from smolvm import DirectKernelBoot, VMConfig

boot = DirectKernelBoot(root="/dev/vda", init="/init")

config = VMConfig(
    vm_id="cross-backend-vm",
    vcpu_count=1,
    memory=512,
    kernel_path=kernel,
    rootfs_path=rootfs,
    boot_args=boot.render(backend="qemu", arch="host"),
)
```

You can customize the profile when you need to:

```python
boot = DirectKernelBoot(
    root="/dev/vda",
    init="/init",
    console="serial",
    rw=True,
    quiet=False,
    extra_args=("acpi=off",),
)
```

Set `SMOLVM_VERBOSE_BOOT=1` in your environment to drop the default `quiet` flag without changing your code. This is useful when debugging boot failures.

### Pick the right kernel for your backend

SmolVM publishes the same Linux 6.12.85 kernel in two formats. Firecracker loads the ELF artifact, while QEMU loads the Image/bzImage artifact. `ensure_base_kernel_for_backend(...)` picks the right one, downloads and verifies it on first use, and caches it under `~/.smolvm/images/`:

```python
from smolvm import DirectKernelBoot, VMConfig, ensure_base_kernel_for_backend

backend = "qemu"
kernel = ensure_base_kernel_for_backend(backend, arch="host")

config = VMConfig(
    vm_id="cross-backend-vm",
    vcpu_count=1,
    memory=512,
    kernel_path=kernel,
    rootfs_path=rootfs,
    boot_args=DirectKernelBoot(root="/dev/vda", init="/init").render(
        backend=backend,
        arch="host",
    ),
)
```

Use this whenever you supply your own rootfs but want SmolVM's verified kernel, for example when testing one image on macOS with QEMU and Linux with Firecracker.

## Real-world example: OpenClaw

<Tip>
  For day-to-day use, run `smolvm openclaw start` — it boots from a [pre-built image](/smolvm/concepts/published-images) in seconds and forwards your `OPENROUTER_API_KEY` and `OPENCLAW_GATEWAY_TOKEN` automatically. The example below shows the manual builder path, which is useful when you're customizing the image.
</Tip>

This example from `examples/openclaw.py` builds a 4 GB Ubuntu image for the OpenClaw application:

```python
import os
from smolvm import SmolVM, VMConfig
from smolvm.build import ImageBuilder, SSH_BOOT_ARGS
from smolvm.utils import ensure_ssh_key

private_key, public_key = ensure_ssh_key()

builder = ImageBuilder()
kernel, rootfs = builder.build_ubuntu_ssh_key(
    ssh_public_key=public_key,
    name="ubuntu-ssh-key-openclaw-4g",
    rootfs_size_mb=4096,
)

config = VMConfig(
    vcpu_count=1,
    memory=2048,
    kernel_path=kernel,
    rootfs_path=rootfs,
    boot_args=SSH_BOOT_ARGS,
    env_vars={
        "OPENROUTER_API_KEY": os.getenv("OPENROUTER_API_KEY", ""),
    },
)

with SmolVM(config, ssh_key_path=str(private_key)) as vm:
    vm.run("apt-get update && apt-get install -y nodejs npm")
    vm.run("npm install -g openclaw")
```

## Troubleshooting

When an image build fails, SmolVM diagnoses the root cause and returns a specific error message. You do not need to debug Docker issues manually.

<AccordionGroup>
  <Accordion title="Docker not installed">
    SmolVM raises an `ImageError` with install instructions:

    * **macOS**: Install [Docker Desktop](https://www.docker.com/products/docker-desktop)
    * **Linux**: `sudo apt-get install docker.io` (Ubuntu)

    You can check Docker availability before building:

    ```python
    builder = ImageBuilder()
    if not builder.check_docker():
        print(builder.docker_requirement_error())
    ```
  </Accordion>

  <Accordion title="Docker daemon not running">
    Start the Docker service:

    <Tabs>
      <Tab title="macOS">
        ```bash
        open -a Docker
        ```
      </Tab>
      <Tab title="Linux">
        ```bash
        sudo systemctl start docker
        ```
      </Tab>
    </Tabs>
  </Accordion>

  <Accordion title="Permission denied on Docker socket">
    Add your user to the `docker` group:

    ```bash
    sudo usermod -aG docker $USER
    newgrp docker  # or log out and back in
    ```
  </Accordion>

  <Accordion title="Build fails with disk space errors">
    Image builds require sufficient disk space. Check available space and clean the Docker cache if needed:

    ```bash
    df -h ~/.smolvm/images/
    docker system prune -a
    ```
  </Accordion>
</AccordionGroup>
