title: "Custom images"
description: "Build, describe, and launch SmolVM sandboxes from your own root filesystem images"
---

Custom images let you start a sandbox with the operating system packages, files, and startup behavior your workload already needs. SmolVM now treats custom images as first-class inputs: you describe the image with `BootImage`, then launch it with `SmolVM.from_image()`.

## How custom images work

The current custom image flow has four parts:

1. Build or provide a root filesystem image.
2. Describe that image with `BootImage`.
3. Launch it with `SmolVM.from_image(...)`.
4. Let SmolVM create an isolated per-VM disk, resize it, and grow the filesystem when supported.

<Note>
  A root filesystem is the disk image that becomes `/` inside the guest. SmolVM supports `raw-ext4` images and QEMU `qcow2` images.
</Note>

## Quick start

This example builds an SSH-capable Alpine root filesystem from a Dockerfile, then launches it as a QEMU sandbox.

```python  theme={null}
from smolvm import DockerRootfsBuilder, DirectKernelBoot, SmolVM

dockerfile = """
FROM alpine:3.20

RUN apk add --no-cache openssh
RUN echo 'root:smolvm' | chpasswd
RUN sed -i 's/#PermitRootLogin prohibit-password/PermitRootLogin yes/' /etc/ssh/sshd_config
RUN sed -i 's/#PasswordAuthentication yes/PasswordAuthentication yes/' /etc/ssh/sshd_config
RUN ssh-keygen -A

COPY init /init
RUN chmod +x /init
"""

init_script = """#!/bin/sh
set -eu

mount -t proc proc /proc || true
mount -t sysfs sysfs /sys || true
mount -t devtmpfs devtmpfs /dev || true
mkdir -p /dev/pts /run/sshd /tmp
mount -t devpts devpts /dev/pts || true
mount -t tmpfs tmpfs /tmp || true

ip link set lo up || true
ip link set eth0 up || true
udhcpc -i eth0 -q -t 5 || true

/usr/sbin/sshd
exec tail -f /dev/null
"""

image = DockerRootfsBuilder(
    name="python-tools",
    dockerfile=dockerfile,
    context={"init": init_script},
    rootfs_size_mb=1024,
    ssh_capable=True,
).ensure(
    backend="qemu",
    boot=DirectKernelBoot(),
)

with SmolVM.from_image(
    image,
    backend="qemu",
    network="slirp",
    memory_mb=1024,
    disk_size_mb=2048,
    grow_filesystem=True,
    ssh_password="smolvm",
) as vm:
    result = vm.run("cat /etc/os-release")
    print(result.output)
```

<Warning>
  `DockerRootfsBuilder` does not install SmolVM's guest agent or SSH server for you. Your Dockerfile and init process must start the services you want to use. Set `ssh_capable=True` only when the guest can accept SSH connections.
</Warning>

## Build from a Dockerfile

Use `DockerRootfsBuilder` when you want to build a raw ext4 root filesystem from a Dockerfile.

```python  theme={null}
from smolvm import DockerRootfsBuilder, DirectKernelBoot

builder = DockerRootfsBuilder(
    name="worker-image",
    dockerfile="""
FROM debian:bookworm-slim
RUN apt-get update && apt-get install -y --no-install-recommends \
    ca-certificates curl python3 openssh-server \
    && rm -rf /var/lib/apt/lists/*
COPY init /init
RUN chmod +x /init
""",
    context={"init": "#!/bin/sh\nexec /bin/sh\n"},
    rootfs_size_mb=2048,
    fingerprint_inputs={"app_version": "2026-06-06"},
)

image = builder.ensure(
    backend="qemu",
    boot=DirectKernelBoot(init="/init"),
)
```

`DockerRootfsBuilder` caches builds by input. It rebuilds when the Dockerfile, build context, build args, Docker platform, rootfs size, or `fingerprint_inputs` change.

<Tip>
  Use `fingerprint_inputs` for values that should invalidate the cache even when they are not files in the Docker build context, such as an application version or dependency lock hash.
</Tip>

## Launch a custom image

Use `SmolVM.from_image()` to turn a `BootImage` into a running sandbox.

```python  theme={null}
from smolvm import SmolVM

with SmolVM.from_image(
    image,
    vm_id="worker-1",
    backend="qemu",
    vcpus=2,
    memory_mb=2048,
    disk_size_mb=4096,
    grow_filesystem=True,
) as vm:
    print(vm.status)
```

`from_image()` reads boot metadata from the image and applies runtime settings such as CPU, memory, backend, networking, mounts, port forwards, vsock, and the communication channel.

## Resize the per-VM disk

Custom images use isolated per-VM disks by default. That means SmolVM copies or materializes the base image before booting the sandbox, so resizing the sandbox does not mutate the original image artifact.

```python  theme={null}
vm = SmolVM.from_image(
    image,
    disk_size_mb=8192,
    grow_filesystem=True,
)
```

Use `disk_size_mb` to request a larger isolated disk at launch time.

Use `grow_filesystem=True` when the image is `raw-ext4` and you want SmolVM to expand the guest filesystem after resizing the disk.

<Note>
  `grow_filesystem=True` currently supports raw ext4 images. For `qcow2` images, SmolVM can resize the virtual disk, but it does not grow the guest filesystem for you.
</Note>

## Describe an existing raw ext4 image

If you already have a root filesystem image, create a `BootImage` directly.

```python  theme={null}
from pathlib import Path

from smolvm import BootImage, DirectKernelBoot, SmolVM, ensure_base_kernel_for_backend

image = BootImage(
    name="existing-alpine",
    rootfs_path=Path("/var/lib/images/alpine-rootfs.ext4"),
    rootfs_format="raw-ext4",
    kernel_path=ensure_base_kernel_for_backend("qemu", arch="host"),
    boot=DirectKernelBoot(),
    backend="qemu",
    ssh_capable=True,
)

with SmolVM.from_image(image, backend="qemu", ssh_password="smolvm") as vm:
    print(vm.run("uname -a").output)
```

`DirectKernelBoot` renders backend-specific kernel arguments for Firecracker, QEMU, and libkrun. For example, Firecracker needs `pci=off`, while QEMU on arm64 uses a different serial console.

## Boot a QEMU firmware image

Use `FirmwareBoot` for images that boot through firmware, such as a QEMU cloud image or a disk with its own bootloader.

```python  theme={null}
from pathlib import Path

from smolvm import BootImage, FirmwareBoot, SmolVM

image = BootImage(
    name="ubuntu-cloud",
    rootfs_path=Path("/var/lib/images/ubuntu.qcow2"),
    rootfs_format="qcow2",
    boot=FirmwareBoot(),
    backend="qemu",
    ssh_capable=True,
)

with SmolVM.from_image(
    image,
    backend="qemu",
    network="slirp",
    memory_mb=2048,
) as vm:
    print(vm.status)
```

Firmware images must use the QEMU backend. They do not set `kernel_path`, `initrd_path`, or `boot_args` because the guest kernel lives inside the disk image.

## Use ImageBuilder for SSH-ready images

`ImageBuilder` is still useful when you want SmolVM to build an SSH-ready Alpine or Debian image for you. You can wrap its output in `BootImage` and launch it through `from_image()`.

```python  theme={null}
from smolvm import BootImage, DirectKernelBoot, ImageBuilder, SmolVM

builder = ImageBuilder()
kernel, rootfs = builder.build_alpine_ssh(rootfs_size_mb=1024)

image = BootImage(
    name="alpine-ssh",
    rootfs_path=rootfs,
    rootfs_format="raw-ext4",
    kernel_path=kernel,
    boot=DirectKernelBoot(),
    backend="firecracker",
    ssh_capable=True,
)

with SmolVM.from_image(image, backend="firecracker", ssh_password="smolvm") as vm:
    print(vm.run("whoami").output)
```

## Troubleshooting

<AccordionGroup>
  <Accordion title="The VM starts, but run() fails">
    `run()` needs a communication path into the guest. Use an SSH-capable image, pass the right SSH credential to `SmolVM.from_image()`, and set `ssh_capable=True` on the `BootImage`.
  </Accordion>

  <Accordion title="The Docker build is not rerunning">
    `DockerRootfsBuilder` uses a fingerprinted cache. Change the Dockerfile, build context, build args, Docker platform, rootfs size, or `fingerprint_inputs` to force a rebuild.
  </Accordion>

  <Accordion title="grow_filesystem=True fails">
    Filesystem growth currently supports raw ext4 images. For qcow2 images, omit `grow_filesystem` and grow the filesystem inside the guest with the operating system's own tools.
  </Accordion>

  <Accordion title="QEMU cannot inspect or resize the disk">
    Install `qemu-img`. On Debian or Ubuntu, run:

    ```bash
    sudo apt-get update && sudo apt-get install -y qemu-utils
    ```
  </Accordion>
</AccordionGroup>
