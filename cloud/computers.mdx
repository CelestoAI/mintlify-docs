The Computers API gives your code or agent an isolated Linux computer. You create a computer, run work inside it, and then stop, start, or delete it when your workflow is done.

## Computer lifecycle

<Steps>
  <Step title="Create">
    Create a new computer from `scratch` or a template such as `coding-agent`.
  </Step>
  <Step title="Run">
    Execute shell commands, inspect output, and publish ports when a service needs a public URL.
  </Step>
  <Step title="Manage">
    Get details, list computers, stop and start long-lived computers, or delete temporary computers.
  </Step>
</Steps>

Choose a [named size](/cloud/features/resources) to set CPU, memory, and disk together. For example, Micro has 2 GB of memory and Large has 16 GB. Celesto assigns the computer's name. Save its ID in your own records if you need to associate it with a job, user, or label.

When you call `POST /v1/computers` directly, send an `Idempotency-Key` header. Reuse that key and the original request body if you retry the same create request. The SDKs send a key for you.

Stop and start to keep the disk, not the running processes. Restart your app after starting the computer again. If deleting a computer returns HTTP `409` while it is `creating`, wait for creation to finish and retry the delete. See [Keep files between sessions](/cloud/features/persistence).

## What to know before running commands

- Scratch includes a shell and basic network tools. Use `coding-agent` when you need Python or Node.js. Don't depend on `systemctl --user` on Scratch; start your application explicitly or use a template that provides the service manager it needs.
- `/exec` takes a command of up to 10,000 characters and a timeout from 1 to 300 seconds. It returns the result after the command finishes. It does not accept standard input or provide a file upload or download endpoint. To send input interactively, [open a terminal connection](#open-a-terminal-connection).
- Don't put credentials in command text or print them in command output. Command text can appear in error logs; a command output expiration time is not a log retention guarantee.

## Create a computer

Use `CloudComputer()` for a fresh `scratch` computer. The `with` block starts it, waits until it is ready, and deletes it when you leave the block.

```python create_computer.py
from celesto import CloudComputer

with CloudComputer(size_id="micro") as computer:
    print(computer.id)
```

Choose another named size when you need more resources:

```python create_sized_computer.py
from celesto import CloudComputer

with CloudComputer(size_id="standard") as computer:
    print(computer.id)
```

<ParamField body="size_id" type="string">
  A [named size](/cloud/features/resources), such as `micro` or `standard`. Cloud computers do not accept CPU, memory, or disk overrides.
</ParamField>

<ParamField body="template_id" type="string" default="scratch">
  Sandbox template ID. Pass `coding-agent` when your agent needs common coding tools already installed.
</ParamField>

<ParamField body="template_version" type="string">
  Optional immutable template version. Pin this when you want repeatable builds as a template changes over time.
</ParamField>

<ParamField body="network_policy" type="object" default='{"mode": "open"}'>
  Outbound internet setting, fixed when you create the computer. Use `{"mode": "off"}` to create an offline computer. Requires Celesto SDK `0.0.13` or later.
</ParamField>

See [Network Control](/cloud/features/network-control) for Python, TypeScript, and CLI examples.

## Use a template

A template is a ready-made setup with tools installed. For built-in templates, your named size determines CPU, memory, and disk. Use `coding-agent` for common coding workflows:

```python create_from_template.py
from celesto import CloudComputer

with CloudComputer(template_id="coding-agent", size_id="micro") as computer:
    result = computer.run("python3 --version")
    print(result.stdout.strip())
```

To start every computer with your own packages installed, build a [custom template](/cloud/features/custom-templates) and pass its `tpl_...` ID as `template_id`.

## Run commands

```python run_command.py
from celesto import CloudComputer

with CloudComputer(size_id="micro") as computer:
    result = computer.run("ls -la /home", timeout=60)
    print(result.stdout)
    print(result.exit_code)
```

<ResponseField name="exit_code" type="integer" required>
  Exit code of the command. `0` means success.
</ResponseField>

<ResponseField name="stdout" type="string" required>
  Standard output from the command.
</ResponseField>

<ResponseField name="stderr" type="string" required>
  Standard error output from the command.
</ResponseField>

## Stream command output

Use `run_stream()` when your code expects an iterator of command events. On Cloud, the events come from the completed `/exec` response, not from a live stream. For live terminal output, open a terminal connection instead.

```python stream_command.py
from celesto import CloudComputer, CommandExitEvent, CommandOutputEvent

with CloudComputer(size_id="micro") as computer:
    for event in computer.run_stream("uname -a"):
        if isinstance(event, CommandOutputEvent):
            print(event.data, end="")
        elif isinstance(event, CommandExitEvent):
            print(f"\nexit code: {event.exit_code}")
```

Each event has a `type` field:

- `started` — command metadata, including `command_id` and `timeout_seconds`. Cloud yields it after receiving the result.
- `stdout` and `stderr` — output text in `data`, when present.
- `exit` — the completed result, including `exit_code`, `duration_ms`, and `timed_out`.

If the request fails, the iterator raises an error rather than yielding an `exit` event. Breaking out of the loop doesn't cancel a remote command.

## Get and list computers

List your cloud computers in the dashboard or with the CLI:

```bash
celesto computer list --cloud
```

To reconnect in Python, use `CloudComputer.get(computer_id)` with the ID of an existing computer.

## Publish a port

Publishing a port gives your computer a public HTTPS URL. Anyone with the URL can connect without a Celesto API key. Add authentication to your app before publishing anything sensitive.

Pick any application port from `1024` through `65535`. A computer can have up to four ports published at a time, and Celesto system ports are reserved for the platform.

Use an existing computer with an app listening on port `8000`. See [Publish ports](/cloud/features/publish-ports) to start and check a sample app.

```python publish_port.py
from celesto import CloudComputer

computer = CloudComputer.get("einstein")
route = computer.publish_port(8000)
print(route.url)

for port in computer.published_ports():
    print(f"{port.port} -> {port.url} ({port.status})")

computer.unpublish_port(8000)
```

## Open a terminal connection

Use `terminal().attach()` to open an interactive shell on a running computer. Your account must have write access to it.

```python terminal.py
from celesto import CloudComputer

computer = CloudComputer.get("einstein")
computer.terminal().attach()
```

## Create a computer

Use `Computer.create()` to get a fresh `scratch` computer. The API can return while the computer is still `creating`. Save the ID, then call `refresh()` until `status` is `running` before running commands or publishing ports.

```ts create-computer.ts
import { Computer } from "@celestoai/sdk";

const computer = await Computer.create();
console.log(computer.name);
console.log(computer.id);
console.log(computer.status);
```

Choose another named size when you need more resources:

```ts create-sized-computer.ts
import { Computer } from "@celestoai/sdk";

const computer = await Computer.create({ sizeId: "standard" });

console.log(`${computer.name} has ${computer.vcpus} vCPUs`);
console.log(`${computer.ramMb} MB RAM`);
```

<ParamField body="sizeId" type="string">
  A [named size](/cloud/features/resources), such as `micro` or `standard`. Cloud computers do not accept CPU, memory, or disk overrides.
</ParamField>

<ParamField body="templateId" type="string" default="scratch">

<ParamField body="networkPolicy" type="object" default='{ mode: "open" }'>

## Stream command output

Use `runStream()` when your code expects an async iterator. Cloud buffers the `/exec` result and yields output only after the command finishes. `execStream()` is an alias. For live terminal output, open a terminal connection instead.

```ts stream-command.ts
import { Computer } from "@celestoai/sdk";

const computer = await Computer.get("einstein");

for await (const event of computer.runStream("uname -a", { timeout: 30 })) {
  if (event.type === "stdout" || event.type === "stderr") {
    process.stdout.write(event.data);
  } else if (event.type === "exit") {
    console.log(`\nexit code: ${event.exitCode}`);
  }
}
```

The iterator yields `stdout` and `stderr` events when output is present, then an `exit` event with `exitCode`. If the request fails, the iterator throws instead of yielding `exit`. Passing an `AbortSignal` stops the client from waiting; a command the computer already accepted can keep running. Check its effects before retrying.

## List recent commands

Retrieve metadata for commands recently executed on a computer, including their exit codes, durations, and command IDs. This is useful for auditing what an agent has run.

```ts list-command-history.ts
import { Computer } from "@celestoai/sdk";

const computer = await Computer.get("einstein");
const history = await computer.listCommandHistory({ limit: 20 });

for (const entry of history.commands) {
  console.log(entry.commandId, entry.status, entry.exitCode);
}
```

## Stop, start, and delete

```ts lifecycle.ts
import { Computer } from "@celestoai/sdk";

import { setTimeout as delay } from "node:timers/promises";

const computer = await Computer.create({ sizeId: "micro" });
console.log(computer.id); // Keep the ID so you can recover if a wait times out.

async function waitFor(status: "running" | "stopped") {
  const deadline = Date.now() + 60_000;
  while (computer.status !== status) {
    if (Date.now() >= deadline) {
      throw new Error(`Computer ${computer.id} did not reach ${status}. Check its status before retrying.`);
    }
    await delay(1_000);
    await computer.refresh();
  }
}

await waitFor("running");
await computer.stop();
await waitFor("stopped");
await computer.start();
await waitFor("running");
await computer.delete();
```

## Open a terminal connection

Use `createTerminalSession()` when you are building your own interactive terminal against a Celesto computer, for example to power a web terminal in your own product. It calls `POST /computers/{id}/terminals` and returns a short-lived, direct connection to Celesto's fast terminal gateway. Your account must have write access to the computer.

```ts terminal.ts
import WebSocket from "ws";
import { Computer } from "@celestoai/sdk";

const computer = await Computer.get("einstein");
const session = await computer.createTerminalSession();

const ws = new WebSocket(session.url);
ws.on("message", (data) => process.stdout.write(data));
ws.on("open", () => ws.send("echo hello\n"));
```

<Warning>
  `session.url` embeds a short-lived terminal token. Treat it as a secret: pass it straight to your WebSocket client, do not log it, and do not send it to a browser you do not control. Use `session.expiresAt` to know when to create a new session.
</Warning>

<ResponseField name="terminalId" type="string" required>
  Durable terminal session ID.
</ResponseField>

<ResponseField name="gatewayUrl" type="string" required>
  Base gateway URL without credentials. Combine with `token` yourself only when you cannot use `url` directly.
</ResponseField>

<ResponseField name="token" type="string" required>
  Short-lived terminal token. Treat this as a secret.
</ResponseField>

<ResponseField name="expiresAt" type="string" required>
  ISO 8601 timestamp after which the token stops working. Create a new session before this time.
</ResponseField>

<ResponseField name="url" type="string" required>
  Authenticated `wss://` URL ready to pass to a `WebSocket` constructor.
</ResponseField>

<Info>
  `getTerminalConnection()` is retained as a deprecated alias for `createTerminalSession()` and calls the same fast terminal gateway endpoint. Update existing code to `createTerminalSession()` at your convenience.
</Info>

## Computer response fields

<ResponseField name="id" type="string" required>
  Unique identifier for the computer, such as `cmp_abc123`.
</ResponseField>

<ResponseField name="name" type="string" required>
  Auto-generated display name for the computer, such as `einstein`.
</ResponseField>

<ResponseField name="status" type="string" required>
  Current status. One of: `creating`, `running`, `stopping`, `stopped`, `starting`, `restoring`, `restorable`, `deleting`, `deleted`, or `error`.
</ResponseField>

<ResponseField name="vcpus" type="integer" required>
  Number of virtual CPUs allocated.
</ResponseField>

<ResponseField name="ram_mb" type="integer" required>
  Memory allocated in MB. TypeScript exposes this as `ramMb`.
</ResponseField>

<ResponseField name="disk_size_mb" type="integer" required>
  Disk allocated in MB. TypeScript exposes this as `diskSizeMb`.
</ResponseField>

<ResponseField name="template_id" type="string" required>
  Sandbox template the computer was created from. TypeScript exposes this as `templateId`.
</ResponseField>

<ResponseField name="template_version" type="string">
  Pinned template version, if one was provided at create time. TypeScript exposes this as `templateVersion`.
</ResponseField>

<ResponseField name="connection" type="object">
  Connection details for accessing a running computer.

  <Expandable title="Connection properties">
    <ResponseField name="ssh" type="string">
      SSH connection string for terminal access.
    </ResponseField>

    <ResponseField name="access_url" type="string">
      URL for browser-based access to the computer.
    </ResponseField>
  </Expandable>
</ResponseField>
