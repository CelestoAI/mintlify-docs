A Celesto custom template is a reusable setup for cloud computers, with your tools already installed. You write the setup commands once, such as installing `ffmpeg` or a set of Python packages, and Celesto runs them for you. Every computer you create from the template then starts with those tools ready, so your agent can get to work right away instead of installing the same packages on every run.

<Note>
  Custom templates require the `celesto` Python package **0.1.6** or later (`pip install -U celesto`) and a Celesto Cloud API key in `CELESTO_API_KEY`. See [Get a Celesto Cloud API key](/cloud/authentication).
</Note>

## How Celesto custom templates work

A custom template has three parts:

- **A base template.** One of the built-in templates, such as `coding-agent`. Your template starts with the tools the base already includes.
- **A build script.** Shell commands that install what you need. Celesto runs the script once, when it builds the template.
- **A template ID.** An ID that starts with `tpl_`. Pass it anywhere you would pass a built-in template ID.

Building takes a few minutes. When the build finishes, Celesto saves the result as an image (a saved copy of the computer's disk that new computers start from). Creating a computer from your template is then as fast as creating one from a built-in template.

## Create a custom template and use it

<Steps>
  <Step title="Create the template">
    Pass a name and your setup commands. Write the commands as a shell script, one command per line.

    ```python create_template.py
    from celesto import Template

    template = Template.create(
        name="data-env",
        base_template_id="coding-agent",
        build_script="""
    apt-get install -y ffmpeg postgresql-client
    pip install pandas polars duckdb
    """,
    )
    print(template.id, template.status)
    ```

    <Check>
      The template is created right away with status `queued`, and Celesto starts building it.
    </Check>
  </Step>

  <Step title="Wait for the build">
    `wait()` follows the build and returns when the template is ready. Pass `on_log=print` to see the build output as it runs.

    ```python
    template.wait(on_log=print)
    ```

    <Check>
      `wait()` returns when `template.status` is `ready`.
    </Check>
  </Step>

  <Step title="Create a computer from the template">
    `create_computer()` returns a [Celesto cloud computer](/cloud/computers) that starts from the custom template. Like any Celesto computer, it is created when the `with` block starts and deleted when it ends.

    ```python
    with template.create_computer() as computer:
        print(computer.run("ffmpeg -version").stdout)
    ```

    <Check>
      The output starts with `ffmpeg version`, which shows the computer started with your packages already installed.
    </Check>

    You can also pass the template ID directly:

    ```python
    from celesto import CloudComputer

    with CloudComputer(template_id="tpl_0123456789ab") as computer:
        print(computer.run("ffmpeg -version").stdout)
    ```
  </Step>
</Steps>

## Choose a base template

A custom template's base template decides which tools your build script can use and which features the cloud computer supports. Pick one of these built-in templates:

| Base | Includes | Good for |
|------|----------|----------|
| `scratch` | `bash`, `curl`, `sudo` | Minimal images where you install everything yourself |
| `coding-agent` | `git`, `python`, `pip`, `uv`, `node`, `npm`, `pnpm`, `rg`, `fd`, `jq` | Most templates. This is the default. |
| `browser-agent` | Everything in `coding-agent`, plus Playwright (a browser automation library), Chromium, and a virtual display (an on-screen desktop the browser can draw to) | Agents that browse the web. Experimental. |

Bases are always built-in templates, so build each custom template from one of these three.

## Choose the computer size for a custom template

Computers from a template get the base template's size unless you choose one. When your packages need more room, pass all three size settings together: `vcpus` (virtual CPU cores), `ram_mb` (memory in MB), and `disk_size_mb` (disk space in MB). Use the values from one of the [named computer sizes](/cloud/features/resources#choose-a-named-size). This example uses Large: 4 vCPUs, 16 GB of memory, and a 60 GB disk.

```python
template = Template.create(
    name="ml-env",
    build_script="pip install torch",
    vcpus=4,
    ram_mb=16384,
    disk_size_mb=61440,
)
```

The finished image must fit in `disk_size_mb`, so give large installs such as `torch` or CUDA a bigger disk. Every computer created from the custom template gets this size. Celesto always builds custom templates on a large machine, whatever size you choose.

## Write the custom template build script

The build script runs once, as root (the administrator account, so you can install system packages directly), inside a fresh copy of the base template. Keep these rules in mind:

- **The first failing command stops the build.** The script runs in strict mode (`set -euxo pipefail`), so make sure each command works on its own.
- **List packages in the script.** The build receives only the script text, so name each package directly, such as `pip install pandas polars`. Commands that read local files, such as `pip install -r requirements.txt` or `./setup.sh`, fail.
- **Answer prompts in advance.** Use `apt-get install -y` so `apt` installs packages straight away instead of stopping for a yes or no answer.
- **Install services, start them later.** The image keeps installed files, not running programs. Install a service such as PostgreSQL in the script, then start it on the computer when you need it.
- **Stay within the limits.** A script can be at most 64 KB, and a build can run for at most 30 minutes.

Check a script before you create a template. `lint()` reviews it in seconds and returns warnings, so you catch mistakes before you spend a build on them:

```python
from celesto import Template

warnings = Template.lint("apt-get install ffmpeg\npip install -r requirements.txt")
for warning in warnings:
    print(f"line {warning.line}: {warning.message}")
```

## Fix a failed custom template build

When a build fails, `wait()` raises `TemplateBuildError`. The error names the failing line, its exit code, and a hint for common mistakes:

```python
from celesto import TemplateBuildError

try:
    template.wait()
except TemplateBuildError as error:
    print(error)                      # the failing line and exit code
    print(error.failure.line_number)  # also: line, exit_code, hint
    print(template.logs())            # the end of the build log
```

Fix the script, then build again:

```python
template.edit(build_script="apt-get install -y ffmpeg\npip install pandas")
template.rebuild().wait(on_log=print)
```

<Tip>
  While a template rebuilds, new computers keep starting from its previous successful build.
</Tip>

Common failures and fixes:

<AccordionGroup>
  <Accordion title="command not found">
    The base template doesn't include that command. Pick a base that has it, or install it earlier in the script.
  </Accordion>
  <Accordion title="externally-managed-environment">
    The system Python refuses `pip install`. Use the `coding-agent` base, whose `pip` installs into its own environment, or create a virtual environment (a private Python setup that `pip` can install into) in the script.
  </Accordion>
  <Accordion title="Unable to locate package">
    `apt` doesn't know the package name. Check the spelling and the package name for Ubuntu.
  </Accordion>
  <Accordion title="The build timed out">
    The build ran past 30 minutes. Remove large downloads, or combine packages into fewer install commands.
  </Accordion>
</AccordionGroup>

## Manage custom templates

Use these Python methods to create, check, build, use, and delete custom templates.

| Method | What it does |
|--------|--------------|
| `Template.create(name=..., build_script=...)` | Create a template and start its build |
| `Template.get("tpl_...")` | Load an existing template |
| `Template.list()` | List your organization's templates, newest first |
| `Template.lint(script)` | Check a script without building |
| `template.wait(on_log=print)` | Wait until the build is ready, printing its log |
| `template.logs()` | Get the latest build log |
| `template.edit(name=..., build_script=...)` | Change the name, the script, or the computer size |
| `template.rebuild()` | Build again with the current script and the latest base |
| `template.create_computer()` | Get a cloud computer that starts from the template |
| `template.delete()` | Delete the template |

Organization members can create templates and use them; viewers can list and use them. Editing, rebuilding, and deleting a template need an organization admin.

## Custom template limits and errors

- **2 builds at a time.** An organization can have 2 builds queued or running. A third raises `CloudAPIError` with status 429 (too many requests); wait for one to finish, then try again.
- **One build per template.** Rebuilding while a build is queued or running raises `CloudAPIError` with status 409 (conflict).
- **Unique names.** Template names are unique within an organization. Reusing a name raises `CloudAPIError` with status 409.
- **A ready build first.** Creating a computer before the first build succeeds raises an error that says to call `wait()` first.

Every `CloudAPIError` message says what to do next, and `error.status_code` holds the HTTP status.

`wait()` keeps retrying through rate limits (temporary caps on how many requests you can send), server errors, and network errors until its timeout (40 minutes by default), because the build keeps running on Celesto either way. When the timeout passes, it raises `OperationTimeoutError`; call `wait()` again to keep waiting.

## Custom template fields

<ResponseField name="id" type="string">
  Template ID, starting with `tpl_`. Pass it as `template_id` to create computers.
</ResponseField>

<ResponseField name="status" type="string">
  Build state: `queued`, `building`, `ready`, `failed`, or `needs_rebuild`. `needs_rebuild` means the base template changed and the template must be rebuilt before it can create computers.
</ResponseField>

<ResponseField name="base_template_id" type="string">
  The built-in template the build started from.
</ResponseField>

<ResponseField name="build_script" type="string">
  The setup commands Celesto runs during a build.
</ResponseField>

<ResponseField name="failure" type="TemplateBuildFailure | None">
  Where the last build failed, when its script exited with an error: `line`, `line_number`, `exit_code`, and `hint`.
</ResponseField>

<ResponseField name="vcpus" type="integer">
  Virtual CPU cores for every computer created from this template. `ram_mb` (memory in MB) and `disk_size_mb` (disk space in MB) work the same way.
</ResponseField>
